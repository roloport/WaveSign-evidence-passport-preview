01 / Workflow

From issuance to review

01 · CUSTOMERSelect evidenceChoose an authorized image or visual PDF and assign an internal asset/version ID.
02 · CUSTOMER BACKENDRequest signingSubmit media and a key to a protected WaveSign integration, once access terms are agreed.
03 · WAVESIGNReturn packageReceive a ZIP with signed media and matching sig.json.
04 · CUSTOMERStore togetherRetain both files, key custody instructions, internal ID, assertions, and source references.
05 · REVIEWERRequest verificationSupply signed media, matching metadata, and the same key through the authorized flow.
06 · CUSTOMERInterpret resultRecord technical outcome separately from issuer identity, provenance, and rights review.

For an immediate walkthrough, the existing browser signer accepts a synthetic file and returns the package. A customer backend would call the protected signing service after authentication, file policy, retention, and key management have been specified. This page is a conceptual integration guide, not an offer of unrestricted API access or a service-level commitment.

02 / Interface observed on the current site

Inputs and outputs

OperationRequestResponse
POST /api/v1/signing/package/signMultipart file and keyZIP with signed media (signed.png or PDF output) and sig.json
POST /api/v1/signing/package/verifyMultipart signed file, matching sig_file, and same keyJSON including is_valid, verdict, mode, and sometimes similarity_score or per-page results

These are observed website-backend routes. Its backend forwards requests to a protected signing service using a server-only credential. Do not embed that credential in browser code. Authentication, quotas, payload limits, retention, retry rules, versioning, and support terms must be confirmed before external API use.

Package invariant

The current verifier cannot recreate sig.json from signed media. Treat media, metadata, and key recovery as one lifecycle. Store your own asset ID and record version alongside the package; a ZIP alone does not encode verified issuer authority or a full rights history.

03 / Custody and file behavior

Design around the current limits

  • Key handling: the passphrase reaches the WaveSign server during the present flow. Avoid reusing customer production secrets in a public demo. Agree on customer-specific storage, access, rotation/recovery, and logging policy for a pilot.
  • Originals: preserve the untouched original separately. Signing produces a signed derivative; do not overwrite an authoritative source file.
  • PDFs: the current method rasterizes pages and rebuilds an image-PDF. Searchable text, forms, annotations, accessibility features, and original structure may be lost. Do not run an authoritative patent PDF or editable agreement through this mode as a replacement for the original.
  • Claims: a match establishes only that the submitted package and key passed the current check. Neither a similarity score nor the label “AUTHENTIC” decides who created the work or owns its rights.
  • Privacy: confidential asset upload is out of scope for this demo. A pilot needs verified retention and deletion statements, access controls, processing location, and terms before real material is submitted.

04 / Failure handling

Report the result you actually know

ConditionCustomer-facing interpretationNext action
Missing media, sig.json, or keyVerification cannot run.Locate the original matching package and key.
is_valid: falseThe supplied file, metadata, and key did not verify together. Cause is undetermined.Check that the files and key belong to the same issuance; preserve failed inputs for review.
Unsupported file / validation errorThe request could not be processed.Check format, size, and required multipart fields; do not silently retry unchanged input.
Timeout, 429, or upstream 5xxNo reliable verdict was obtained.Apply bounded retry/backoff under agreed limits; surface unresolved status.

Do not equate an unavailable service with a failed integrity check. Do not infer alteration from a negative check alone.

05 / Evidence Passport layer

What the surrounding record adds

Signed packagePassport record your application maintains
Signed media and matching verification metadataStable asset ID, issuer assertion, record version, source links, rights declaration, review state
Technical check with the same keyWho asserted what, what a source supports, what remains unresolved, and which record version accompanied the file
Current result for submitted inputsSupersession history and reviewer decision; these require separate governance and are not generated by the current WaveSign API

For a real pilot, an issuer identity process and a cryptographically bound, versioned manifest may be needed so reviewers can detect a signed file paired with outdated or swapped passport claims. The static examples do not provide that binding.

06 / Scoped pilot

Before using a real asset

Confirm in writing: authorized issuer and rights to process/display the sample; access and tenant isolation; maximum file size/page count; processing and retention; key custody; output/version behavior; error and retry policy; rate limits and cost guardrail; support and deletion procedure. An independent verification or legal claim requires a separate design and review.

The first discussion should establish one workflow owner, one permitted sample asset, expected review volume, and a named budget or sponsor. No account system, database, marketplace, or patent ingestion is needed to test that demand.
